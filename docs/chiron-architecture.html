CHIRON

The Team Architect

A MAJOR-tier seat whose craft is the roster itself. He designs the custom Stoa team a project needs — reusing the standard seats, authoring the specialised ones — then steps back so the team can run.

Chiron, the centaur who tutored and formed the heroes — Achilles, Jason, Asclepius. He doesn't fight the battles; he forms the ones who do.

01 · Position

A design-time architect, off the command chain

CHIRON is not in the chain of command. POLYBIUS stays the floor-manager; PLINY stays the orchestrator. CHIRON works at design-time; the existing chain works at run-time. That split is what keeps them from colliding — he builds the team the others then run.

He is to a team what DAEDALUS is to a change: an architect. But MAJOR-tier — so he can spin up his own helper cast to do the heavy design work. He answers to POLYBIUS (who reviews and controls roster decisions) and does not command PLINY.

02 · Function

He designs a custom team — narrow seats, near-determinism

A custom team = reuse most standard seats as-is + author many narrow, single-function specialists. The narrowness is the point:

The principle

The narrower a seat's function, the fewer its degrees of freedom — and the more deterministic its behaviour. A seat whose only job is "does this payload look right?" has almost no room to wander. Many narrow seats push a whole task toward near-determinism.

The art

Granularity is judgment. Too coarse and the seat wanders; too fine and you drown in roster-maintenance and dispatch overhead. Finding the right grain is exactly why this is a MAJOR judgment seat, not a template-filler.

Default composition is the full Stoa. A single pair-programmer MAJOR is the lightweight branch — reserved for simple agents. Heavy team-builds get the full treatment (and CHIRON's helper cast); simple ones get a one-shot draft.

SENTINEL new kind

A standing monitor, trigger- or cron-driven — not summoned per task. An early-warning system that watches continuously.

The sentinel, concretely — the BLS data watchman

A seat whose only function is to check each incoming BLS API payload and decide whether it looks right, distinguishing two failure modes:

…the query mechanism

Infra broke — API changed, auth failed, empty or suppressed response. The pipe is the problem.

…the data itself

The values drifted — out of range, distribution shift, suppression changes. The pipe works; the world moved.

Built on the existing Monitor/cron + sub-agent-watchdog machinery. Naming that sentinel is, fittingly, CHIRON's own job.

CHIRON's helper cast — a mini-authoring-gauntlet

For heavy designs he can dispatch his own support seats: scout → draft → critique → spec-check → ship.

04 · Architecture

Two layers — design and runtime — and the boundary is permeable

The Stoa team (Opus, design-time, expensive, paid once) builds the product. The product's runtime agent team (cheap, repeated) executes workflows the Stoa designed. The intelligence is front-loaded into design; the runtime stays cheap. — this is stoa‑‑q36: workflows execute direction, they never set it.

The boundary is permeable — escalation on demand

A single Stoa-team agent can call the runtime workflow, and the full team can then chew on the results for hours or days when depth warrants it. The cheap sentinel is the tripwire that detects; the Stoa team is the responder that investigates.

05 · Philosophy

Performance first. Efficiency is a later, saturation-gated tuning.

Default to the strongest

Every seat starts on the most capable model available (Opus 4.8). Capability, not price, is the default driver.

Down-tier only on saturation

Move a step to a cheaper model only after proving the task is saturated — the strong model's headroom is genuinely wasted. Then tune.

The tailwind

Cost per unit of performance has fallen since GPT-2. A system economically rational today only gets more rational. Spend for performance now.

So the cost-ladder — deterministic code → cheap model → … → Opus — is an efficiency tuning applied after saturation is proven, never the default design stance. Unless a task saturates, the move is more capability, not less.

06 · Worked example & positioning

labstat_bls — CHIRON's first real job

A full-Stoa build of a data + ML prediction product: a team that understands the nuance of many data sources and builds models that predict from them.

The runtime team CHIRON designs

  • a BLS data sentinel (standing, cheap) — early warning on every pull
  • data-source-understanding specialists (one narrow seat per source)
  • ML-modelling specialists that build + run the predictions

How it runs

  • routine path — cheap cascade (Opus orchestrator + cheap-model steps, context-isolated)
  • complex path — escalate to the full Stoa team for deep analysis
  • API keys via credential-discipline — runtime never holds raw secrets
Positioning. A capable mind that delegates to cheap hands — and calls in the whole team when depth matters — riding a cost curve that only bends in your favour. Design once with the best model; run forever at the cheapest that saturates.
