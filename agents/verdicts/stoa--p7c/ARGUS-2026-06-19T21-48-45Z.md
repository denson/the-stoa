## R1 -- the convention-vs-enforcement ruling (FULL REASONING)

Ruling: convention-with-structural-backstop is ADEQUATE. I CONFIRM the section-35.5 carve-out. No scope change. No escalation.

The section-35.5 test is precise: is this a process/role-file/tooling change with NO runtime attack path? Applied directly:

1. No new runtime attack surface. Sign-everywhere + caller-sid + the registry introduce no network endpoint, no credential flow, no privilege boundary, no access gate. The registry is read-only audit data. The sign-tag is provenance metadata. The caller-sid is derived from a LOCAL filesystem path. Nothing here is consumed as an AUTHORIZATION input by any control.

2. The forgeable-provenance property does not CREATE a new harm -- it inherits a pre-existing one. The cm- commons is already a shared bw store where ANY agent can already write ANY comment under any [from:] it likes. That was true before this arc. Sign-everywhere IMPROVES auditability (a forged tag can now be cross-checked against stoa--reg + the on-disk transcript); it does not introduce a NEW trust dependency an attacker could exploit that did not exist yesterday. The threat (an agent forges a [from:]) is not NEW -- and no mechanism built in this arc TRUSTS the tag as a gate. Forgery buys the forger nothing it did not already have.

3. The structural backstops are real and I verified them. (a) The section-28.1 prepare-commit-msg git-trailer hook + squash-merge preservation is genuine structural enforcement for the GIT channel (verified at op-disc 28.1/28.3). (b) The registry audit cross-check (a [from:] caller-sid validates against stoa--reg + the on-disk <slug>/<caller-sid>.jsonl) is a real detect-side backstop, and I confirmed the on-disk transcript that anchors it actually exists.

4. The section-35.5 category-error guard applies. Demanding a threat->mitigation map of a provenance CONVENTION would be the exact category error 35.5 names -- there is no M<n> for a convention to defeat. A full structural bw write-wrapper (the enforcement option) is EXPLICITLY out of the directive locked scope (design section-5 + directive out-of-scope), and the directive locked the WHAT to a convention (the rejected-overkill was per-agent GitHub accounts).

Why this is a CONFIRM and not a reject: the only way R1 becomes ENFORCEMENT-REQUIRED is if some mechanism in THIS arc begins to TRUST the provenance tag as an access-control input (then a forged tag = a real privilege bypass = a named runtime threat). No such mechanism is built here. The registry is audit, not authz. So the honest classification is not threat-ratified and convention-with-backstop is adequate FOR THIS FIRST IMPLEMENTATION.

Honest-claim boundary (section-35.5): the moment a FUTURE arc wires the provenance tag into an authorization decision (e.g. only the seat whose caller-sid matches X may close ticket Y), R1 re-opens as a named runtime threat and the enforcement question MUST be re-ratified. That is a future-arc trigger, not a this-arc blocker. Recommend the design or the stoa--reg ticket body carry a one-line note to that effect so the boundary is not lost -- non-load-bearing nicety, not a gate.

## R3 -- registry race (FULL REASONING)

Ruling: the race is eliminated for the PRIMARY path; the design does NOT need explicit serialization added.

The launcher mints BOTH seat ids in one process and records them in a SERIAL post-launch loop (design section-6 item 1(e): call record-seat.ps1 serially for each seat). Two serial calls from one process cannot race each other -- no concurrency on the primary path. The caller-sid amendment shrinks the surface further: sub-agents no longer self-record at all (they sign inline), so the ONLY registry writers are terminal seats. Confirmed sound.

The ONE residual (r3 above, non-load-bearing): the FALLBACK self-record path (desktop sessions running whoami then self-recording). Two desktop seats self-recording near-simultaneously is a read-modify-rewrite of one JSONL path. The design ASSERTS this surfaces as a loud git conflict; I could not find where bw GUARANTEES conflict-vs-clobber for same-path concurrent attaches. Bounded (the dogfood seed is launcher-driven = serial; desktop concurrent-self-record is rare) and NON-load-bearing, but surfacing it: if you want belt-and-suspenders, have record-seat.ps1 re-read-and-verify its own row after attach (read-after-write check), OR document that concurrent desktop self-record is unsupported and the launcher path is canonical. NOT a gate -- a hardening note.

## MUST/SHOULD -- the runtime caller-sid existence check (FULL REASONING)

Ruling: MUST.

rev2 changed the failure mode of a CC-layout drift from SAFE (rev1 emitted no id) to UNSAFE (rev2 emits a confidently-wrong caller-sid -> a provenance chain to the WRONG parent). The whole POINT of this arc is to make cm- commons provenance TRUSTWORTHY; a mechanism that can silently emit a wrong-but-confident parent attribution actively undermines the arc own thesis. The runtime on-disk existence check (emit caller-sid ONLY if <slug>/<caller-sid>.jsonl exists; else degrade to mnemonic-only + warning) converts the unsafe confident-wrong back into the safe degrade rev1 had -- at the cost of one test -f. Per the cost-calculus (a near-free check that closes a confident-misattribution hole) and per the seat raison-detre (trustworthy provenance), a SHOULD is too weak: a future CC layout change would silently re-introduce exactly the confident-wrong failure the check exists to prevent, and SHOULD gives the implementer license to skip it. Make it MUST. P5(c) already asserts it at VERIFY time; the RUNTIME check protects every real invocation after the gauntlet closes. The two together (verify-time P5(c) + runtime MUST) are the correct belt-and-suspenders.
