## FINDINGS

### F1 — P-FALLBACK has NO reader: signal file written but nothing reads it (SEVERITY HIGH, load_bearing TRUE; design section 2.1 + section 3 P-FALLBACK + directive Verified-premise P-FALLBACK clause)
quadrant_classification: easy-easy

Directive requires: the check writes a drift-signal file that a RELIABLE carrier reads (the Stop self-check and/or CLAUDE.md), and surfacing must never depend on additionalContext ALONE. The design WRITES .claude/.substrate-drift-signal (section 2.1 L83) but wires NO non-additionalContext reader.
EVIDENCE: grep -rn substrate-drift-signal over .claude/ + substrate/ + CLAUDE.md returns ZERO readers. The named carrier stop-self-check.sh (read in full) carries a FIXED A/B/C checklist (L90-94) and does not read the signal file. No CLAUDE.md tier mentions it.
The design actual fallback (section 2.1 L57, section 3 P-FALLBACK step 3) is the hook OWN throttle-path re-surface — re-emitting via emit_additionalContext_json on the next start. That is the SAME additionalContext channel the fallback is supposed to be independent of. By the directive own words this defeats P-FALLBACK: surfacing collapses back onto additionalContext-alone when additionalContext is the failed channel. The on-disk file is human-readable, but no SUBSTRATE carrier (Stop hook / CLAUDE.md) is wired to surface it to the model — which is exactly what the directive mandates. Load-bearing gap, not a polish item.

### F2 — Relocation silently moves the check.sh state-file baselines (two-levels-up coupling) (SEVERITY HIGH, load_bearing TRUE; design section 4 + section 2.2)
quadrant_classification: hard-easy

Both check.sh scripts compute their per-workspace state-file location as the directory TWO LEVELS ABOVE the script.
EVIDENCE: check-substrate-updates/check.sh L34-35 (SCRIPT_DIR then a SUBSTRATE_DIR resolved as SCRIPT_DIR + ../..); check-bw-release/check.sh header L7-8 + L38-41 (the directory two levels above this script — substrate/ at substrate-tier, workspace/.claude/ at consumer-tier). Baselines (.substrate-last-check, .bw-release-last-check, .substrate-manifest) live at that two-up dir.
Currently substrate/skills/check-substrate-updates/check.sh maps two-up to substrate/. After section-4 relocation to substrate/maintenance/check-substrate-updates/check.sh, two-up maps to substrate/maintenance/ — baselines move with it (WRONG anchor). The design section 4 does NOT address this depth-coupling; it treats relocation as a pure move. Section-4-alt (delete only SKILL.md, dirs stay) does NOT trip this because the two-up depth is unchanged.

### F3 — Hook hard-codes .claude/skills/check-*/check.sh, contradicting the section-4 relocate-out-of-skills decision (SEVERITY HIGH, load_bearing TRUE; design section 2.1 vs section 4)
quadrant_classification: easy-easy

The hook pseudocode invokes the checks at a HARD-CODED skills path: CWD + .claude/skills/check-substrate-updates/check.sh and CWD + .claude/skills/check-bw-release/check.sh (design section 2.1 L63-64). But section 4 RELOCATES the dirs OUT of skills/, so at consumer tier they deploy to .claude/maintenance/... not .claude/skills/... The hook path will not resolve post-relocation — the SessionStart check silently does nothing (FAILs-OPEN to empty output, so the failure is INVISIBLE: no drift ever surfaces).
EVIDENCE: design section 2.1 L63-64 (hard-coded skills/ path) vs section 4 L285 (relocate to substrate/maintenance/). The section 2.1 NOTE (L65-69) CLAIMS the hook resolves BOTH candidate paths and uses whichever exists, but the pseudocode implements only the single skills/ path. Internal inconsistency between the headline decision (section 4) and the hook logic (section 2.1). Compounded: the design never specifies WHERE substrate/maintenance/ lands at consumer tier — there is NO generic install.sh deploy mechanism for non-skill operator dirs (the cited substrate/githooks/ precedent is a HARD-CODED special-case block at install.sh L1528-1546, not a reusable pattern), so the deploy-path the design says it adds is unspecified.

### F4 — Relocation xref blast radius materially understated; section-4-alt avoids F2/F3/F4 entirely (SEVERITY MEDIUM, load_bearing TRUE for pass-A scope; design section 2.7 + section 4 + section 5 weak-point 2)
quadrant_classification: easy-hard

The design says about 6 canon cross-references. The actual surface is denser: MAJOR_POLYBIUS.md L512 AND L624 each carry MULTIPLE inline check-skill path refs inside single dense paragraphs; op-disc L373 + L967; module substrate-update-check.md L12 (a RECOMPOSED module — MODULE-INLINE marker at MAJOR_POLYBIUS L379, so the edit must hold through the install.sh recompose); bw-upgrade.md L15/L47/L59 (check-bw-release refs, INCLUDING the two-levels-above-the-script baseline-location prose that F2 makes stale). Each is load-bearing canon; the XREF probe catches a DANGLING path but not a SEMANTICALLY-wrong-but-present one (DAEDALUS own weak-point 2).
The section-4-vs-section-4-alt scope call (THE floor-manager decision — I surface, do not decide): section-4-alt (delete only the two SKILL.md files, leave check.sh/apply.sh/revert.sh dirs in place under substrate/skills/) avoids F2, F3, AND F4 simultaneously — dirs do not move so the two-up baseline anchor is unchanged (no F2), the hook .claude/skills/check-*/check.sh path still resolves (no F3), and zero xrefs go stale (no F4). I verified section-4-alt closes the stale-LIEUTENANT trap: gen-data-lib.ts L100-101 skips a dir with no SKILL.md (fs.existsSync then continue), so deleting the SKILL.md removes it from discoverSkillFiles discovery exactly as relocation would. The design only objection to section-4-alt — orphaned skill dirs is its own smell — is a tidiness concern, not a load-bearing one. For a housekeeping pass A, section-4-alt is the materially lower-risk choice; the design recommends the HIGHER-blast-radius option and names the lower-risk one only as a fallback. I surface the asymmetry crisply for the floor-manager call.

## P-EMPIRICAL determinism read (DAEDALUS weak-point 1 — scrutinized, NOT a load-bearing blocker)

DAEDALUS self-flagged uncertainty that claude -p headless fires SessionStart startup. gsearch (2026-06-17) resolves this in the design FAVOR on runnability: claude -p DOES instantiate a session and fire the startup matcher. So the probe is RUNNABLE — the interactive fallback is likely unneeded.
BUT the probe ASSERTION is the soft part, exactly as DAEDALUS suspected: PASS-iff-the-model-echoes-a-token couples pass/fail to MODEL INSTRUCTION-FOLLOWING, not to injection. A model can fail to echo for reasons unrelated to whether additionalContext reached it (a false FAIL), or the token could reach the model via the prompt echo rather than the hook. A MORE DETERMINISTIC surface exists and the probe should prefer it: claude --debug hooks writes to stderr the extracted-additionalContext-payload-injected event, and the session transcript JSONL (transcript_path) records the injected context — both assert injection INDEPENDENT of model behavior. Probe-DESIGN improvement (VERA can adopt it), classified easy-hard: I do not block on it; I name the more-deterministic assertion so VERA P-EMPIRICAL green is hard, not soft. Not a load-bearing design risk — a probe-quality finding.
