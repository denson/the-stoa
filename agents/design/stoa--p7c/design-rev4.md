## §1. Problem restatement

Make Stoa agent **identity** first-class and durable so a message on the shared `cm-` commons (or any bw store) carries a structural, machine-resolvable signal of *which seat / role / project / machine* authored it. Four PRINCIPAL-locked requirements (the WHAT is locked; this doc designs the HOW):

1. **LAUNCH** — `launch-team.ps1` mints a per-seat UUID, assigns a space-free human-friendly name, launches `claude` with `--session-id <uuid>` + `--name <name>` (+ optional `--remote-control`), and RECORDS `seat→{session-id, name, project, machine}` durably to a portable bw registry. *(rev4 DC1-simplification: the launcher KEEPS mint+pin for terminal launches; desktop sessions, which cannot pin at creation, self-record via `$CLAUDE_CODE_SESSION_ID` on activation — see DC1.)*
2. **WHOAMI** — a new skill any seat runs to discover its own identity by **reading `$CLAUDE_CODE_SESSION_ID`**: a terminal seat discovers its own session-id; a sub-agent discovers its caller-sid (the dispatching terminal's sid). Covers desktop-UI-created sessions that could not pin `--session-id` at creation. *(rev4: the env var replaces the rev1–rev3 nonce-grep entirely.)*
3. **SIGN-EVERYWHERE** — broaden op-disc §28 so every seat carries its identity in ALL channels (bw comments, git trailers, recordkeeping), preserving the §28 absolute: git `Author:` stays the PRINCIPAL's identity.
4. **REGISTRY** — `seat→{id,name,project,machine}` lives in **bw** (git-synced, portable; session-ids are per-machine so the roster must survive cross-machine).

**Imported assumptions (named, not smoothed):**
- *A1 — session-ids are same-machine handles only.* No cross-machine `--resume`/cloud-sync; the registry records ids for liveness/audit on the minting machine, NOT for cross-machine session resumption. Continuity stays on bw + handoffs. (Directive Settled facts.)
- *A2 — DC1 folds stoa--fpj.* The substrate launcher (171L) lacks `-ArcId`/`-OnlySeat` the deployed copy (200L) has; a blind `install.sh` of the 171L source would REGRESS deployed consumers. Resolving the SSoT inversion is in-scope regardless of fold-vs-sequence.
- *A3 — the origindex builder-publish security model is ORTHOGONAL* (network-access identity: Tailscale/SSO; defines no seat registry). Do not force-converge. The convergence target is the FUTURE builder-deploy launcher, which adopts THIS registry.
- *A4 (rev4 — RETIRED as a load-bearing assumption).* rev1–rev3 rested on the empirical `<slug>/<caller-sid>/subagents/agent-<id>.jsonl` transcript layout (A4) to derive identity by path-parse. **rev4 no longer parses any transcript path** — identity comes from `$CLAUDE_CODE_SESSION_ID`, a documented runtime env var. The transcript layout is no longer a dependency; the only retained runtime dependency is the env var itself (see the new A5).
- *A5 (rev4 — the new load-bearing empirical):* **`$CLAUDE_CODE_SESSION_ID` is set in every Stoa seat's shell env, and resolves to the seat's OWN sid in a terminal session and the CALLER's sid in a sub-agent.** Verified live FOUR independent ways: NOMOS C1/C2/C3 (terminal own-sid + sub-agent caller-sid); FM terminal (`88cd8c37-…`); PLINY terminal (`a3e23bca-…`); and **this rev4 design pass from inside a sub-agent** (`echo $CLAUDE_CODE_SESSION_ID` → `a3e23bca-779d-4ffc-b720-58262af14cdb` = PLINY's caller-sid, NOT a per-agent id). **Corollary (A5b — empirically resolved this pass):** there is **NO env var that cleanly discriminates a terminal seat from a sub-agent** — see the discriminator resolution in DC3. **Corollary (A5c):** there is **NO `CLAUDE_CODE_AGENT_ID` env var** — agent-id is genuinely unavailable from the env, which is why v1 drops it from the sub-agent signature.

### DC1 — FOLD stoa--fpj into the launcher rewrite; HYBRID pin-decision (RESOLUTION: FOLD + HYBRID)

**FOLD decision (VERBATIM from rev3 — ARGUS-CONFIRMED R2).** One coherent rewrite of `substrate/skills/team-launcher/launch-team.ps1` that (a) backports the deployed copy's `-ArcId`/`-OnlySeat` params + their two logic blocks, AND (b) adds the new mint-UUID / assign-name / record-to-registry machinery. **DC1-simplification pin-decision (the redirect opened this; my call): HYBRID — launcher KEEPS mint+pin for terminal launches; desktop self-records from `$CLAUDE_CODE_SESSION_ID`.**

The redirect relaxed locked requirement #1 ("the launcher need not necessarily mint+pin `--session-id` … DAEDALUS's call") now that any seat can self-discover its sid via the env var. The trade-off:
- **(a) mint+pin at launch (terminal launches):** the registry is populated AT launch and the launcher knows the id DETERMINISTICALLY before the seat even activates. Works only where the launcher controls `claude` invocation — i.e. terminal/`wt` launches, NOT desktop-UI-created sessions.
- **(b) self-record on activation (any seat):** the seat reads `$CLAUDE_CODE_SESSION_ID` and writes its own registry row. Works for desktop too (the case the pin can't reach), but the registry is not populated until the seat activates.

**RESOLUTION: HYBRID.** The launcher **keeps** mint+pin+record-at-launch for the seats it launches (the `wt`/terminal path); **desktop sessions self-record** from the env var on activation via the whoami skill + `record-seat.ps1`. Rationale:
- **Honors locked requirement #1 AND the FM's req#1-vs-req#2 flag (22:00Z+).** The FM read req#1 as still requiring the launcher mint+pin for terminal launches and flagged that dropping it would contradict the locked WHAT. The hybrid keeps the launcher pin — so it does NOT collapse req#1's launcher-mint into env-var-self-record. The env var is **complementary** (it solves the desktop case req#1's launcher path structurally cannot reach), not a replacement.
- **Pinning still buys DETERMINISM, which the env var does not.** Even though a pinned `--session-id` equals `$CLAUDE_CODE_SESSION_ID` at runtime (so self-record-from-env always works regardless), the pin lets the launcher know the id AHEAD of activation — so the registry row exists at launch, the launcher can print it deterministically (P1's dry-run shape), and there is no activation-ordering window where a launched seat is un-recorded. Dropping the pin would forfeit that determinism for zero gain on the terminal path.
- **Self-record covers exactly the gap the pin can't.** Desktop-UI sessions (`ENTRYPOINT=claude-desktop` — confirmed the live case on this machine for both the FM and PLINY) are created OUTSIDE the launcher, so the launcher can neither mint nor pin their id. Those seats read `$CLAUDE_CODE_SESSION_ID` on activation and call `record-seat.ps1` themselves. The env var makes this self-record path robust (it always returns the real runtime sid), where rev1–rev3's nonce-grep made it flaky (flush-timing).

So: **launcher = mint + pin `--session-id` + record-at-launch (terminal/`wt` path, deterministic); desktop = self-record from `$CLAUDE_CODE_SESSION_ID` on activation (the only path that reaches desktop sessions).** This is the minimal change from rev3's DC1 (rev3 already mint+pinned; rev4 keeps that and additionally documents desktop self-record as the env-var-powered fallback). NOT a DC1 reduction — a DC1 clarification that the desktop fallback is now env-var-backed instead of nonce-grep-backed.

### DC2 — registry: a dedicated bw ticket whose attachment is a JSONL manifest on the beadwork branch (VERBATIM from rev3)

**Decision.** The registry is a **single dedicated bw ticket** (`stoa--reg`, title `Stoa seat registry — seat→{session-id,name,project,machine}`) whose **durable payload is a JSONL manifest attached on the `beadwork` branch** at `attachments/stoa--reg/seat-registry.jsonl`. One row per active seat; append-by-rewrite (read current, append/replace the row, re-attach). bw comments on the ticket are NOT the roster rows (comments are an append-only log, awkward to query/dedupe); they are a human-readable change-log. The machine-readable roster is the attached JSONL.

**Why this shape over the alternatives:**
- *vs comments-as-rows:* comments cannot be updated or removed (a stale/dead seat row would accumulate forever); JSONL is rewriteable, so liveness updates and seat retirement are clean.
- *vs a file committed to `main`:* the beadwork branch is the git-synced portable store that already travels cross-machine (it carries all bw state); `bw attach` writes there and commits with a single-line intent. Putting the roster on `main` would couple roster churn to code history. **`bw attach` is the native, already-portable write path** — `bw attach <id> <file> --name <path>` stores bytes at `attachments/<id>/<path>` on beadwork and commits.
- *vs converging with the origindex security model:* orthogonal (A3) — that is network identity, not a seat roster.

**Record schema (one JSON object per line):**
```json
{"seat":"POLYBIUS_the-stoa","name":"Polybius_the_Stoa","session_id":"990b0750-5572-4836-b9c7-18d626a12e96","project":"the-stoa","machine":"<hostname>","role":"floor-manager","tier":"project","launched_at":"2026-06-19T21:00:00Z","status":"alive"}
```
Fields: `seat` (the canonical `ROLE_slug` mnemonic, the `[for:]` address), `name` (human-friendly, space-free, non-unique), `session_id` (the unique handle; per-machine), `project` (slug), `machine` (hostname — disambiguates per-machine ids), `role`, `tier`, `launched_at` (ISO-8601 Z), `status` (`alive` | `retired`). `session_id` may be `null` for a seat that has not yet self-discovered (e.g. a desktop session pre-whoami); `name`+`seat`+`machine` still identify it.

The registry rows are for **terminal seats** (they have a `session_id`); ephemeral sub-agents are not registry rows — their provenance is signed inline (caller-sid) and is anchored to their parent's registry row via the caller-sid, so the roster stays small and live-seat-shaped. (A sub-agent's caller-sid IS a terminal seat that the registry already tracks.)

**Write recipe (how a seat records itself) — the REAL-execution-testable path:**
A tiny helper `record-seat.ps1` (ships beside the launcher in the team-launcher skill dir) that:
1. `git show beadwork:attachments/stoa--reg/seat-registry.jsonl` → current manifest (empty string if absent).
2. Drop any existing line whose `(seat,machine)` matches (idempotent re-record / liveness refresh).
3. Append the new JSON line; write to a temp file.
4. `bw attach stoa--reg <temp> --name seat-registry.jsonl` (overwrites the stored path verbatim; commits to beadwork).

This is callable **standalone, without spawning a live agent session** — the launcher calls it per seat after computing `{seat,name,session_id,project,machine}` (terminal path), a desktop seat calls it on activation with its env-var-discovered sid (self-record path), and VERA calls it directly with a synthetic row (see P3). The launcher's `-DryRun` PRINTS the intended `record-seat.ps1` invocation but does NOT execute it; the REAL round-trip is exercised by calling `record-seat.ps1` directly.

**Read recipe (PRINCIPAL: "which seat owns which project / is it alive"):**
`git show beadwork:attachments/stoa--reg/seat-registry.jsonl` → pipe through `jq` (or PowerShell `ConvertFrom-Json`) filtered on `project` / `status=="alive"`. Documented in the registry's own bw-ticket body + the team-launcher SKILL.md.

**Adoptability by the future builder-deploy launcher (DC2 single-roster requirement):** the schema is launcher-agnostic (`seat`/`project`/`machine` carry no the-stoa-specific assumption) and the write recipe is a standalone PS1 the builder launcher calls the same way. One registry, one ticket, one schema — the builder-deploy work ADOPTS `record-seat.ps1` + `stoa--reg`, it does not stand up a second roster.

### DC3 — sign-everywhere: BROADEN §28 via a new sibling subsection §28.9 (RESOLUTION; rev4 sub-agent row = env-var caller-sid, agent-id dropped)

The §28 absolute is restated verbatim and PRESERVED: git `Author:` stays PRINCIPAL; identity layers ON TOP, never in place of.

**The terminal-vs-sub-agent signing distinction (rev4 — env-var-sourced; agent-id dropped for v1):**

|---|---|---|---|---|
| **Terminal seat** (top-level session: POLYBIUS/PLINY, any `--session-id`-launched or desktop-created seat) | `$CLAUDE_CODE_SESSION_ID` = its OWN sid | `session_id` = `$CLAUDE_CODE_SESSION_ID` | `[from: <Name> \| sid <session-id> \| <project>]` | existing §28.1 `Co-Authored-By` + optional `Stoa-Session-Id: <sid>` trailer |

**FAIL-LOUD guarantee (FIX 1, re-homed — MUST):** both sign formats above require `$CLAUDE_CODE_SESSION_ID` to be present (non-empty). If the var is empty/unset, whoami **MUST FAIL-LOUD** (clear stderr error, non-zero exit) rather than emit a blank or guessed sid — there is no workaround to fall back to (PRINCIPAL-locked). This is the env-var analog of rev3's MUST on-disk existence check: it converts a missing-identity condition into a loud failure, never a silent or confident-wrong sign-tag. See DC4.

**The terminal-vs-subagent discriminator (MY design call — resolved EMPIRICALLY this pass): seat-role-knowledge, NOT env-detection.**

The question: how does a seat / the whoami skill know whether to label `$CLAUDE_CODE_SESSION_ID` as `sid` (terminal) vs `caller-sid (subagent)`? I probed it empirically (the redirect instructed me to): from inside THIS sub-agent run I dumped `env | grep CLAUDE_CODE` and diffed it byte-for-byte against PLINY's terminal dump.

**Evidence (the env-diff, this pass):**
```
diff (PLINY terminal CLAUDE_CODE_*)  (my sub-agent CLAUDE_CODE_*)  →  IDENTICAL (zero differences)
```
Both sets are byte-for-byte the same, including `CLAUDE_CODE_CHILD_SESSION=1` (set in PLINY's TERMINAL too — so it does NOT discriminate), `CLAUDE_CODE_ENTRYPOINT=claude-desktop` (same in both), and the ABSENCE of any `CLAUDE_CODE_AGENT_ID`. The only var carrying identity, `CLAUDE_CODE_SESSION_ID`, is `a3e23bca-…` in BOTH my sub-agent env and PLINY's terminal env — because a sub-agent inherits its caller's sid (that IS the capability). **Conclusion: NO env var cleanly discriminates terminal from sub-agent** (this matches the FM's and PLINY's independent observations of `CHILD_SESSION=1` in their terminals).

**RESOLUTION: the discriminator is SEAT-ROLE-KNOWLEDGE, applied by the §28.9 convention — not env auto-detection.** A seat KNOWS its own class from its role file: a MAJOR (POLYBIUS/PLINY) is a terminal seat by construction; a CAPTAIN dispatched via the Agent tool (ADA/VERA/CATO/ARGUS/DAEDALUS) is a sub-agent by construction. The §28.9 convention selects the sign-format by the seat's known class, and whoami returns the bare value with a `--role terminal|subagent` hint that the CALLER supplies from its known class:
- **whoami contract:** `whoami` reads `$CLAUDE_CODE_SESSION_ID`, FAIL-LOUDs if empty, and prints the bare sid (exit 0). It takes an OPTIONAL `--role terminal|subagent` hint that ONLY selects the OUTPUT LABEL (`sid=<v>` vs `caller-sid=<v>`); the underlying value is the same env var either way. With no `--role`, whoami prints the bare value and a note that the §28.9 convention (keyed on the seat's known class) picks the label. **whoami does NOT try to auto-detect the class** — the empirical finding is that it CANNOT (no discriminator), and a guess would be worse than the role-knowledge the seat already has.
- **Why this is correct, not a workaround:** the seat's class is not ambiguous information that needs runtime detection — it is STRUCTURAL (a MAJOR role file vs an Agent-tool dispatch). The label is a presentation choice the convention makes; the VALUE (the sid) is what the env var authoritatively supplies. Trying to env-detect a fact the seat already knows from its role would be the bolt-on the PRINCIPAL's rule rejects.

This is dogfooded by THIS design pass: I am a sub-agent CAPTAIN (known by construction — I was dispatched via the Agent tool by PLINY), so I sign `[from: CAPTAIN_DAEDALUS_the-stoa (subagent) | caller-sid a3e23bca-779d-4ffc-b720-58262af14cdb]` — caller-sid sourced from `$CLAUDE_CODE_SESSION_ID`, NOT nonce-grep, NOT path-parse. My caller-sid `a3e23bca-…` IS PLINY's terminal session (the seat that dispatched me), which the registry tracks as a terminal row — so my provenance chains to a revivable parent. Terminal seats (the floor-manager, PLINY) sign with `sid`, as they already did on this charter ticket.

**caller-sid: self-discovery from the env var is the SOLE source (no brief-passed cross-check needed).** rev3 carried an optional `--expect-caller-sid` brief cross-check against the path-parse-derived value. rev4 simplifies: `$CLAUDE_CODE_SESSION_ID` IS the runtime-authoritative caller-sid (the runtime sets it; there is no weaker path-derived value to cross-check against). The brief-passed cross-check is therefore DROPPED as redundant — the env var is ground truth. (A dispatch brief MAY still state the caller-sid for human readability, but whoami does not need it and does not validate against it.)

### DC4 — whoami skill: read `$CLAUDE_CODE_SESSION_ID`; FAIL-LOUD if empty; nonce-grep fully retired (RESOLUTION — env var)

The skill is now a few lines.

**The whoami algorithm (rev4):**
1. Read `$CLAUDE_CODE_SESSION_ID` from the environment.
2. **MUST — FAIL-LOUD if empty/unset (FIX 1, re-homed):** if the var is empty or absent, print a clear stderr error (`whoami: $CLAUDE_CODE_SESSION_ID is not set; cannot determine session identity`) and **exit non-zero** (e.g. exit 2). Do NOT fall back to nonce-grep, path-parse, or any other workaround — there is none, by PRINCIPAL ruling. This is the only failure path.
3. Print the bare sid to stdout; exit 0. The value is the seat's OWN sid in a terminal session and the CALLER's sid in a sub-agent — the runtime sets this; whoami does not classify it.
4. **Optional `--role terminal|subagent` hint (LABEL only):** with `--role terminal`, print `sid=<value>` (or `--json` → `{"kind":"terminal","session_id":"<value>"}`). With `--role subagent`, print `caller-sid=<value>` (or `--json` → `{"kind":"subagent","caller_sid":"<value>"}`). With NO `--role`, print the bare value + a one-line note that the §28.9 convention (keyed on the seat's known class) selects the label — because, as established empirically (A5b), no env var discriminates the class and the seat already knows its class structurally.

**Output contract:**
- Success (var present) → bare sid on stdout, exit 0. (`--role`/`--json` shape the label/structure as above; `--verbose` also echoes that the source was `$CLAUDE_CODE_SESSION_ID`.)
- FAIL-LOUD (var empty/unset) → stderr error, exit 2. **No degraded-but-zero path** — unlike rev3's sub-agent-degrade-to-mnemonic (which existed because the path-parse could derive a sid whose parent transcript was missing), there is no "partial identity" condition here: either the runtime gave us a sid or it did not, and "did not" is a loud failure.

**Why this is simpler AND more robust than rev3's nonce-grep DC4:**
- **No flush-timing.** rev3 needed an emit-then-grep-on-a-subsequent-turn dance because the nonce had to flush to disk before the grep could find it; rev4 reads an env var that is set at process start.
- **No layout fragility.** rev3's path-parse depended on the `<slug>/<caller-sid>/subagents/agent-<id>.jsonl` internal layout (A4), which a Claude Code update could change. rev4 depends only on the documented `$CLAUDE_CODE_SESSION_ID` env var.
- **The sub-agent half is now REAL-runnable in one call** (FIX 2 satisfied more cleanly): a sub-agent runs `echo $CLAUDE_CODE_SESSION_ID` and gets its caller-sid immediately — no `--classify-path` simulation needed for a class VERA can't BE.

**Store-root portability:** N/A for the identity read (it is a single env-var read, no filesystem traversal). The `record-seat.ps1` write path (DC2) still resolves the beadwork store via `git show beadwork:…` (portable, no hard-coded user path), unchanged from rev3.
